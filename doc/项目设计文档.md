# bm-cli 项目设计文档（v0.1）

## 1. 项目背景

`bm-cli` 基于 `beautiful-mermaid` 仓库能力构建，目标是提供一个对 AI Agent 友好的 Mermaid 渲染运行时，而不是传统的人类交互式命令行工具。

当前仓库已具备核心引擎能力：

- SVG 渲染：`renderMermaid()`
- 终端渲染：`renderMermaidAscii()`（Unicode/ASCII）
- 主题系统：`THEMES`、`fromShikiTheme()`
- 支持图类型：Flowchart/State、Sequence、Class、ER

## 2. 产品目标

- Agent 优先：默认非交互，输入输出均为可机器解析协议。
- 终端直出：支持不落盘地在终端展示图表。
- 中英文支持：错误信息和文本响应支持 `zh` + `en`。
- 低资源占用：执行完成即退出，避免内存长期驻留。

## 3. 非目标

- 不做 TUI 图形化界面。
- 不依赖浏览器截图链路（如 Playwright）作为核心路径。
- 不优先优化人类手动参数交互体验（可兼容但非主路径）。

## 4. 架构总览

`bm-cli` 采用三层结构：

1. `CLI Adapter Layer`
- 解析命令与标准流输入，做参数校验与错误映射。

2. `Agent Protocol Layer`
- 负责请求/响应 schema、版本兼容、错误码稳定输出。

3. `Render Engine Layer`
- 调用现有仓库导出的 `renderMermaid()` 与 `renderMermaidAscii()`。

## 5. 命令设计（Agent-First）

### 5.1 `bm agent capabilities`

返回能力声明，供 agent 自适配。

- 支持的图类型
- 支持的输出格式
- 支持的主题
- schema 版本
- 语法能力声明（`syntaxProfiles`、`defaultSyntaxProfile`、`syntaxModes`）
- 资源限制默认值
- 终端能力检测结果（如 `ghostty` / `kitty-graphics` / `true-color`）
- 渲染模式列表（`ascii`、`unicode`、`image-kitty`）

### 5.2 `bm agent exec --json`

单请求模式，默认从 `stdin` 读取请求 JSON，向 `stdout` 输出响应 JSON。

- 新增渲染器参数：`renderer=auto|text|image`
- `auto` 行为：优先探测终端图形能力，支持则走图片渲染，否则自动回退文本渲染

### 5.3 `bm agent batch --jsonl`

批量模式，一行一个请求，一行一个响应，便于上游流水线并行分发。

### 5.4 `bm term`

终端直接渲染模式，默认读取 Mermaid 文本并输出图表到终端，适配 heredoc/pipe/here-string，无需保存文件。

- 支持 `--renderer auto|text|image`，默认 `auto`
- 支持图形协议的终端（如 Ghostty/Kitty）可直接显示图片
- 非 TTY、CI、pipe 等场景默认回退到文本模式

支持输入方式：

```bash
bm term <<'MM'
graph LR
A[开始] --> B[处理]
B --> C[结束]
MM
```

```bash
echo "graph LR; A-->B" | bm term
```

## 6. 协议设计（JSON）

### 6.1 请求体（草案）

```json
{
  "id": "req-001",
  "schemaVersion": "1.1",
  "op": "render",
  "input": {
    "text": "graph LR; A-->B"
  },
  "output": {
    "format": "terminal-unicode"
  },
  "options": {
    "renderer": "text",
    "syntaxProfile": "normalized-v2",
    "syntaxMode": "strict",
    "theme": "tokyo-night",
    "charset": "unicode",
    "font": "Inter"
  },
  "limits": {
    "timeoutMs": 2000,
    "maxInputBytes": 262144,
    "maxOutputBytes": 1048576
  },
  "locale": "zh"
}
```

### 6.2 响应体（草案）

```json
{
  "id": "req-001",
  "ok": true,
  "data": {
    "terminal": "┌───┐ ...",
    "svg": null
  },
  "error": null,
  "meta": {
    "durationMs": 12,
    "engine": "beautiful-mermaid",
    "version": "0.1.x",
    "renderMeta": {
      "requestedRenderer": "auto",
      "actualRenderer": "terminal-unicode",
      "fallbackReason": null
    }
  }
}
```

### 6.3 协议草案文件索引（v1.1 + v2）

以下文件作为当前可执行草案的单一引用来源（source of truth）：

- `drafts/agent-protocol/capabilities.response.v1.1.draft.json`：`agent capabilities` 响应草案（静态能力 + 运行时探测）。
- `drafts/agent-protocol/agent-exec.request.v1.1.draft.json`：`agent exec` 请求草案。
- `drafts/agent-protocol/agent-exec.response.success.text.v1.1.draft.json`：`agent exec` 文本渲染成功响应草案。
- `drafts/agent-protocol/agent-exec.response.success.image-inline.v1.1.draft.json`：`agent exec` 图片内联成功响应草案（JSON 通道）。
- `drafts/agent-protocol/agent-exec.response.error.v1.1.draft.json`：`agent exec` 失败响应草案（结构化错误）。
- `drafts/agent-protocol/agent-exec.response.error.syntax.v1.1.draft.json`：`agent exec` 语法失败响应草案。
- `drafts/agent-protocol/agent-batch.contract.v1.1.draft.json`：`agent batch --jsonl` 行为契约草案。
- `drafts/agent-protocol/syntax.profile.v1.draft.json`：语法 profile 草案（`core-v1` / `extended-v1` + 模式语义）。
- `drafts/agent-protocol/syntax.profile.v2.draft.json`：语法 profile 草案（`full-v2` / `normalized-v2` + 路线策略）。
- `specs/bm-cli-mermaid-syntax-v2.md`：五类图全量语法规范与规范化规则（Route1）。
- `specs/bm-cli-syntax-implementation-routes.md`：Route1/Route2 实现路线与兼容层策略。

约束说明：

- `agent exec` 与 `agent batch` 的 `stdout` 仅输出 JSON/JSONL，不直接写终端图形协议 escape 数据。
- `image-kitty` 终端图形输出仅用于 `bm term` 人类查看路径。
- Mermaid 语法约束以 `drafts/agent-protocol/syntax.profile.v2.draft.json` 为准（v1 兼容保留）。

### 6.4 语法规范与校验模式（新增）

新增协议字段：

- `options.syntaxProfile`：语法配置名（默认 `normalized-v2`）。
- `options.syntaxMode`：校验模式（`strict|compat|recover`，默认 `strict`）。

模式语义：

- `strict`：未知/禁用语法直接报错，不自动修复。
- `compat`：未知语法告警，禁用语法报错。
- `recover`：未知/禁用语法告警，并允许安全改写（必须返回 `warnings[]`）。

语法配置目标：

- 通过 `full-v2` 提供五类图全量语法支持。
- 通过 `normalized-v2` 保持语义全量同时输出规范化，提升确定性。
- 路线1先完成“全量支持 + 规范化 + Skill 约束”，路线2再增加兼容层自动修复。

## 7. 输出格式设计

- `terminal-unicode`：终端 Unicode 线框图（默认终端模式）
- `terminal-ascii`：纯 ASCII 线框图（最大兼容性）
- `svg`：字符串形式 SVG
- `image-kitty`：终端图形协议图片输出（Ghostty/Kitty 等支持终端）

格式决策：

- `bm term` 默认输出 `terminal-unicode`
- `bm agent exec` 根据 `output.format` 返回对应字段
- 非请求字段一律不输出，保持响应紧凑稳定

### 7.1 渐进式终端渲染（Progressive Rendering）

为兼容不同终端能力，采用三层渲染策略：

1. Level 0：`terminal-ascii`（纯文本，最高兼容）
2. Level 1：`terminal-unicode`（字符画增强）
3. Level 2：`image-kitty`（终端图片直出）

`renderer=auto` 时，执行顺序为：

1. 先做终端能力探测（优先协议探测，不仅依赖环境变量）
2. 若支持 Kitty Graphics Protocol，输出 `image-kitty`
3. 若不支持，则回退 `terminal-unicode`
4. 若字符能力受限，再回退 `terminal-ascii`

回退原因通过 `meta.renderMeta.fallbackReason` 返回，便于 agent 诊断。

## 8. 终端显示与零落盘

为支持 “类似 `<<` 机制” 的无文件流程：

- 全命令支持从 `stdin` 读取输入
- 支持 heredoc（`<<EOF`）、pipe（`|`）、here-string（`<<<`）
- 默认 one-shot 执行，结束即释放进程资源

## 9. 中英文支持策略

- 错误核心依赖机器码 `error.code`，避免语言歧义。
- 文本消息双语输出：
  - `error.messageZh`
  - `error.messageEn`
- `locale` 仅影响消息展示，不影响协议结构与错误码。

## 10. 错误码与退出码

### 10.1 错误码（建议）

- `E_PARSE_HEADER`
- `E_PARSE_SYNTAX`
- `E_SYNTAX_UNSUPPORTED_DIAGRAM`
- `E_SYNTAX_FORBIDDEN_DIRECTIVE`
- `E_SYNTAX_PROFILE_MISMATCH`
- `E_UNSUPPORTED_TYPE`
- `E_INVALID_OPTION`
- `E_TIMEOUT`
- `E_LIMIT_EXCEEDED`
- `E_INTERNAL`

### 10.2 进程退出码（建议）

- `0`：成功
- `2`：请求或参数错误
- `3`：渲染执行失败
- `4`：系统级错误

## 11. 资源与性能设计

- 默认 one-shot：每次请求独立进程，执行后退出。
- 惰性加载：仅按请求格式加载相应渲染路径。
- 限流与超时：
  - `timeoutMs`
  - `maxInputBytes`
  - `maxOutputBytes`
  - `maxDiagramChars`
  - `maxImagePixels`
  - `maxImageBytes`
  - `rasterizeTimeoutMs`
- 可选 daemon 模式（未来）：仅用于高吞吐，必须 `idleTimeoutMs` 自动退出。

## 12. i18n 与 CJK 终端对齐

中文节点在 ASCII/Unicode 终端中存在宽度差异问题，需统一宽度测量策略。

- 引入 CJK 感知宽度计算（如 wcwidth 思路）
- 节点文本宽度计算用于 box 尺寸和边线连接点
- 保障 `zh` 与 `en` 在同一图内布局稳定

## 13. 迭代计划

### Phase 1（MVP）

- `capabilities`

- 稳定 JSON 协议 + 错误码体系

### Phase 2

- `agent batch --jsonl`

- 资源限制与超时保护
- `renderer=auto` 与终端能力探测框架

### Phase 3

- 终端宽度自适配与 CJK 精细对齐

- `image-kitty` 渲染链路（SVG -> PNG -> 协议输出）
- Ghostty/Kitty/WezTerm 差异兼容优化

## 14. 与现有仓库的映射关系

- `renderMermaid()`：用于 `output.format = svg`
- `renderMermaidAscii()`：用于 `terminal-unicode`/`terminal-ascii`
- `theme.ts`：主题枚举、主题映射与色彩配置来源
- 图类型检测逻辑沿用现实现，CLI 不重复实现渲染算法

## 15. 验收标准（MVP）

- Agent 可通过单次 JSON 请求拿到可解析响应。
- 支持 `<<`/`|`/`<<<` 输入，无需落盘文件。
- 终端可直接渲染 Unicode/ASCII 图表。
- 至少支持 `zh` + `en` 的错误消息返回。
- 执行结束后无常驻进程，内存随进程释放。

## 16. 设计优化项与功能意义（借鉴 Obsidian Registry 模式）

### 16.1 版本化 Schema + `validate-request`

- 功能：为 `agent exec` 请求定义版本化 JSON Schema，并提供请求预校验命令。
- 意义：让 agent 在执行前就能发现参数错误，降低运行时失败率；协议演进时可做前向/后向兼容控制。

### 16.2 双层校验输出：`errors[]` + `warnings[]`

- 功能：把校验结果分为阻断错误与非阻断告警。
- 意义：agent 可自动决策“立即失败”还是“带告警继续执行”，同时保留高可读的诊断信息用于自动修复链路。

### 16.3 固定能力声明：`capabilities`

- 功能：稳定返回支持图类型、输出格式、主题、限制上限、schema 版本。
- 意义：agent 无需依赖文档猜测功能，可在运行时自适配调用策略，显著减少不兼容调用。

### 16.4 发布清单：`release-manifest`

- 功能：在发布产物中记录 `version`、`checksum`、`signature`、`minCompatibleSchema`。
- 意义：保证可验证来源与完整性，支持安全升级和回滚，避免升级后协议不兼容导致生产中断。

### 16.5 弃用清单：`deprecations`

- 功能：集中定义即将废弃/已废弃字段、命令、默认值行为及生效时间。
- 意义：给 agent 和调用方稳定迁移窗口，避免“突然 breaking change”。

### 16.6 CI 分层：协议校验 / 渲染回归 / 格式化

- 功能：将流水线拆为独立职责：Schema/契约检查、黄金样例渲染比对、代码与文档格式化。
- 意义：失败原因可快速定位，减少修复时间；防止协议改动误伤渲染行为或样式稳定性。

### 16.7 每日统计与可观测性

- 功能：统计渲染成功率、平均耗时、错误码分布、超时比例等指标。
- 意义：形成数据闭环，支持阈值调优与问题预警，让性能与稳定性优化从“经验驱动”变为“数据驱动”。

## 17. 参考 Obsidian CLI 的设计借鉴与取舍

### 17.1 可借鉴点

- 统一命令语法：采用稳定的 `命令 + 参数 + flags` 结构，降低调用方学习成本。
- 命名空间分组：按职责组织为 `agent:*`、`render:*`、`diag:*`、`dev:*`，避免命令平铺扩散。
- 上下文默认 + 显式覆盖：支持默认 `stdin`/当前路径，同时允许显式 `input=`、`format=` 覆盖。
- 诊断命令优先：提供 `diag:doctor`、`diag:env` 输出环境与兼容性检查，减少集成排障时间。
- 自动化友好：提供 `dev:benchmark`、`dev:trace`、`dev:golden` 便于回归测试与性能分析。

### 17.2 不照搬项（边界）

- 不依赖 GUI 运行态：避免像应用内 CLI 一样依赖主程序已启动，`bm-cli` 保持独立可执行。
- 不放大命令面：优先保持核心命令最小闭环，避免早期命令膨胀增加维护成本。
- 不引入交互阻断：默认非交互，不在执行路径中加入 prompt/确认步骤，保障 agent 流水线稳定。

### 17.3 对当前 `bm-cli` 的落地建议

- 保持 Agent-First 主线：`agent capabilities`、`agent exec`、`agent batch` 作为主入口。
- 补充人类快速入口：保留 `bm term` 供终端即时查看图表，不影响协议主路径。
- 全局参数一致化：统一 `--json`、`--locale`、`--timeout-ms`、`--quiet` 的行为语义。
- 错误输出规范化：诊断命令与执行命令复用同一错误码与返回结构，降低调用复杂度。

## 18. 文稿合理性评审与修订建议

### 18.1 总体结论

- 当前设计方向正确，核心主线（Agent-First、协议化、one-shot 低占用）与现有渲染引擎能力匹配。
- 综合评估为“高合理性”，可直接进入实现阶段，但需对部分建议做边界收敛。

### 18.2 建议优先采纳项（应立即执行）

- CJK 宽度修复：统一终端显示宽度计算，避免中文节点导致边框与连线错位。
- 结构化诊断：落地 `errors[]` + `warnings[]` 与稳定 `error.code`，便于 agent 自修复。
- 执行核心复用：`term` 与 `agent exec` 共享同一执行引擎，避免双实现漂移。
- 确定性输出：同输入同输出，禁止随机字段，支持回归测试与缓存复用。

### 18.3 有价值但需调整的建议

- 模糊解析（Fuzzy Parsing）：改为可选 `recover` 模式，默认严格解析，避免掩盖真实错误。
- 定位信息（range）：在解析阶段保留行列映射后再输出 `range`，保证错误定位可信。
- 布局引擎抽象：先保留当前 `dagre` 实现，抽象接口放入后续阶段（P2）再实施。

### 18.4 需修正的表述与实现边界

- `Capabilities` 不强制放入核心渲染库导出，优先由 `bm-cli` 协议层维护，避免核心库职责膨胀。
- “移除 devDependencies 以减小运行体积”不作为主要手段，重点应放在运行时依赖与打包策略。
- 分发策略不采用单一路径，建议“npm 包 + Bun 单二进制”双轨并行，兼顾兼容性与部署效率。

### 18.5 实施优先级（更新）

- P0：CJK 宽度修复、结构化错误输出、`term/agent` 执行核心统一。
- P1：Schema 校验、`capabilities` 固化、可选 `recover` 解析模式、终端能力探测。
- P2：布局引擎抽象、可观测性深化、性能调优、`image-kitty` 图形渲染增强与分发增强。

### 18.6 本轮新增协议优化项（已确认）

1. `agent --json` 通道与终端图片输出隔离

- 问题：`agent` 协议通道若混入终端 escape 数据，会破坏 JSON 可解析性。
- 规则：`agent exec/batch` 仅输出 JSON/JSONL；`image-kitty` 仅用于 `term`。
- 兼容：Agent 图片需求通过 `png-inline` 或 `png-ref` 字段承载，不直接写 stdout escape。

2. `capabilities` 拆分静态能力与运行时探测

- 问题：固定能力声明与会话环境探测是两类信息，混用会导致语义不清。
- 规则：输出 `capabilities.static`（稳定契约）与 `capabilities.runtime`（本次探测 + 置信度）。
- 参考草案：`drafts/agent-protocol/capabilities.response.v1.1.draft.json`。

3. `renderer=auto` 默认策略按命令上下文区分

- 问题：Agent 主链路优先稳定可解析输出，`auto` 可能引入非预期图片路径。
- 规则：`term` 默认 `auto`；`agent exec/batch` 默认 `text`，仅显式请求启用 `image`。
- 目标：提升确定性输出与流水线稳定性。

4. 错误模型增强“可自动修复”信号

- 现状：已有 `error.code` + 双语消息。
- 规则：新增 `error.category`、`error.retryable`、`error.suggestedAction`。
- 目标：让上游 agent 能自动执行重试、降级、改参。

5. `batch` 语义补齐幂等与部分失败策略

- 问题：仅有批量入口不足以支撑稳定编排，缺少顺序与失败语义。
- 规则：
  - 响应必须返回 `index` + `id/requestId`。
  - 顺序保证：响应顺序与请求顺序一致。
  - 明确 `continueOnError` 及可重试错误白名单。
- 参考草案：`drafts/agent-protocol/agent-batch.contract.v1.1.draft.json`。

6. 版本兼容从“版本号”升级到“协商规则”

- 现状：已有 schema 版本与 deprecations 思路。
- 规则：增加 `minSupportedSchema` / `maxSupportedSchema`，并为弃用项标注生效日期（`removeAfter`）。
- 目标：避免跨版本调用歧义，保障升级窗口可预测。

### 18.7 终端兼容补充优化（纳入 P0/P1 清单）

P0（必须优先完成）：

1. 字宽模型从“CJK 宽度修复”升级为“字素簇宽度规范”
- 背景：当前“仅修 CJK”不足以覆盖多码点 emoji、ZWJ 序列、组合附加符号，仍会出现边框错位。
- 机制：布局计算必须先做 grapheme segmentation，再按 display width 计宽，禁止直接以 `string.length` 参与布局。
- 实施：
  - 在运行时宽度模块中统一提供 `getDisplayWidth/sliceByDisplayWidth/padToDisplayWidth`。
  - 固化 Unicode 规范化策略（默认 NFC）与 East Asian Ambiguous 宽度策略（固定为 1 或 2，不允许环境漂移）。
  - 为 `terminal-unicode` 与 `terminal-ascii` 复用同一宽度算法，避免双实现偏差。
- 验收：同一输入在 Ghostty 与至少 1 个对照终端中不出现边框塌陷、文本溢出、箭头错位。

2. 明确跨终端 emoji 宽度策略并固化为回归基线
- 背景：emoji 在不同终端和字体回退下的列宽感知可能不一致，若无策略定义会导致回归结果不稳定。
- 机制：先决策“固定宽度策略”或“环境跟随策略”，再设计测试；不得先写测试后补策略。
- 实施：
  - 样例至少覆盖：单码点 emoji、肤色修饰符 emoji、ZWJ 组合 emoji、emoji + CJK 混排。
  - 将样例纳入 golden fixtures，并在失败输出中显示“期望宽度/实际宽度”。
  - 文档中明确该策略对 `term` 与 `agent exec` 的一致性要求。
- 验收：同一版本在 `terminal-unicode` 与 `terminal-ascii` 路径下输出行为可预测、可复现。

3. CI 增加“字符网格一致性检查”（headless）
- 背景：仅依赖截图 diff 对环境敏感，不适合做默认 CI 闸门。
- 机制：以“字符网格正确性”作为第一层回归标准，像素回归作为可选增强。
- 实施：
  - 新增 headless 校验脚本，逐行计算 display width，并检查左右边界列一致性、节点框封闭性、连线锚点列对齐。
  - 失败时输出最小定位信息：用例名、行号、列号、期望值、实际值。
  - 覆盖样例包含 CJK、emoji、ZWJ、combining marks、长标签、混排文本。
- 验收：任何宽度/对齐回归都可在 CI 稳定复现并直接定位到具体行列。

P1（协议与运行时增强）：

4. 终端字体回退策略文档化并输出运行时诊断信号
- 背景：部分错位来自字体缺字与 fallback，而不是渲染算法本身，若无诊断会造成误判。
- 机制：把“算法问题”和“字体配置问题”分层输出，避免混合定位。
- 实施：
  - 文档补充 Ghostty 最小建议配置：主等宽字体、CJK fallback、符号/emoji fallback、连字开关建议。
  - 在 `capabilities.runtime` 或 `diag` 输出增加字体风险提示字段（如：疑似 fallback 风险、建议检查项）。
  - 对检测逻辑保持非阻断，只给 warning，不影响主渲染链路成功返回。
- 验收：用户可在首次排障时快速判断是字体覆盖问题还是布局算法问题。

5. ANSI/VT 控制序列引入前的兼容门禁
- 背景：ANSI/OSC 一旦默认输出，容易污染 `agent --json` 通道并破坏机器解析。
- 机制：遵循“协议优先、增强可选”原则，先保证 JSON 通道纯净，再叠加终端增强能力。
- 实施：
  - 默认保持纯文本输出；ANSI/VT 仅允许在 `term` 路径通过显式开关启用。
  - 引入 ANSI/VT 前需完成兼容矩阵（Ghostty/Kitty/iTerm2/Windows Terminal）与降级策略。
  - 若探测失败或环境不支持，必须稳定回退文本模式并返回可诊断 `fallbackReason`。
- 验收：`agent exec/batch` 始终可 JSON 解析；终端增强能力按能力探测安全启用，不影响 Agent 主链路稳定性。
